#### Message Passing Channel: Choosing Between mpsc, broadcast, watch, and oneshot

* mpsc:
    * when to use: aggregator, actor command inbox, worker pools
    * pattern: multi-producer single-consumer work queue with backpressure
      (each item processed by ONE receiver)
* broadcast:
    * when to use: chat room, live market telemetry
    * pattern: multi-producer multi-consumer event stream (every active
      subscriber gets every event; slow receivers can lag)
* watch:
    * when to use: config update, metrics dashboard, service readiness state
    * pattern: single-producer multi-consumer state sync (subscribers only care about the LATEST value; intermediate values may be skipped)
* oneshot:
    * when to use: response channel in actor pattern, task completion result
    * pattern: single-producer single-consumer one-shot reply (single value, auto-cleanup on drop)

#### Router actor pattern for dynamic source registration

* Architecture:
    * Feeds send raw payloads over individual `mpsc` channels; the Router actor owns dedicated forwarding tasks bound to specific `source_id`s.
* Key Properties:
    * Independent Backpressure: A slow or noisy feed's buffer fills up without blocking other feeds.
    * Active Teardown: The Router holds `JoinHandle`s to forcibly abort/unplug misbehaving or closed feeds instantly.
    * Enforced Identity: Payload tagging happens at the port (Router) level, preventing feeds from spoofing `source_id`s.

#### Network Programming

##### Splitting TCP Streams (`into_split`)

> **Why split?**
> 1. **Rust Ownership:** `TcpStream` requires `&mut self` for both reading and
>    writing. Rust forbids two simultaneous mutable references across
>    concurrent tasks.
> 2. **Type Safety:** Separates streams into `OwnedReadHalf` and
>    `OwnedWriteHalf`, preventing accidental cross-reading/writing.

**Key Use Cases:**

* **Connection Keep-Alive / Heartbeats:** Dedicated task sends periodic PINGs on `WriteHalf` while `ReadHalf` waits for incoming data.
* **TCP Bidirectional Proxy / Tunneling:** Forwarding data between two connections simultaneously using `tokio::io::copy`.

```rust
async fn proxy(mut client: TcpStream, mut target: TcpStream) ->
anyhow::Result<()> {
    let (mut client_read, mut client_write) = client.into_split();
    let (mut target_read, mut target_write) = target.into_split();

    // Pipe Client -> Target AND Target -> Client concurrently
    let client_to_target = tokio::io::copy(&mut client_read, &mut
target_write);
    let target_to_client = tokio::io::copy(&mut target_read, &mut
client_write);

    tokio::try_join!(client_to_target, target_to_client)?;
    Ok(())
}
```

##### UDP: `Arc` Sharing, Connected Mode & Buffering

* **Concurrent Access via `Arc` (`&self` vs `&mut self`):**
  * `UdpSocket` operations (`send_to`, `recv_from`) take **`&self`** instead of `&mut self`.
  * The socket leverages OS-level interior mutability for thread safety, so it does **not** need a `Mutex` or a dedicated `.split()` method.
  * Because `Arc<T>` grants multiple shared references (`&T`) across tasks, **`Arc<UdpSocket>` is all that is needed for concurrent read/write tasks.**
  * General `Arc` rule: `Arc<T>` only gives immutable `&T` references. Mutating plain data inside an `Arc` requires `Arc<Mutex<T>>` or `Arc<RwLock<T>>`

* **Connected Mode (`socket.connect(addr)`):**
  * **Kernel Filtering:** The OS drops incoming packets from any source other than `addr`.
  * **Ergonomics:** Use `send()` and `recv()` directly without specifying target addresses on every packet.
  * **ICMP Error Reporting:** Surfaces network delivery failures (e.g., `ConnectionRefused`) directly to subsequent `send`/`recv` calls.

* **Buffer Tuning (`SO_RCVBUF`):**
  * **Silent Packet Loss:** A full UDP socket buffer **never blocks the sender**—the OS kernel silently drops incoming datagrams.
  * **Burst Absorption:** Increasing `SO_RCVBUF` (via the `socket2` crate) provides an OS-level shock absorber for high-frequency burst traffic, giving the Tokio event loop time to drain the socket.
